# lose_all_on_death (CN baseline / English ROM)

New mod. When the player dies, everything they carry is **destroyed**: all weapon records, the
three armour slots, the ring/accessory and the whole 25-slot bag, gold included. Only the
**soul slot** survives. Nothing is dropped on the ground, so the Angel's "take you back" trip
finds nothing to pick up. The bank (character storage) is untouched.

- Definition: `Patches/Definitions/Custom/lose_all_on_death.json` (stage `static_candidate`),
  generated by `Patches/lose_all_on_death/build.py` (assembles, checks every preimage).
- Ship: `Patch_Manager/patches/lose_all_on_death.bps` (102 B, SHA-256 `2a8e7c63…`) and
  `Patch_Manager/patches/cn/lose_all_on_death.bps` (52 B, CN-compatible).
- Writes: `0x0800F4B6` (6 B), `0x0800FB16` (6 B), code `0x080BB3B4` (48 B).
- **Allocation:** `0x080BB3B4..0x080BB3FF` (code uses 48 B; was zero, no literal references in
  the ROM). Owner `lose_all_on_death`. Doesn't collide with the uncommitted
  `slash_shock_paralysis.bps` (`0x080BC321..`, `0x09014000..0x090163FF`).

## The patch

Both copies of the vanilla death drop (below) enter their random-armour loop through a `b`. That
`b` becomes `bl 0x080BB3B4; b <after the loop>`:

| Hook | Resume | Path |
|---|---|---|
| `0x0800F4B6` | `0x0800F54E` | the path hit by About_To_Die (runtime-verified) |
| `0x0800FB16` | `0x0800FBAE` | second copy (static only; same logic, also calls `0x0805B37C`) |

`delete_all()` zeroes the 16-byte owner records `+0x78..+0x2E7` except `+0x138` (soul). It
clobbers r0–r3 only. The vanilla tail then runs unchanged: the slot-flag refreshes
`0x0805D748..0x0805D898`, then the gold drop `0x0805DC70`, which finds no gold and spawns
nothing.

## Runtime A/B (`runtime_verified`, English ROM)

`Tools/.venv/bin/python Patches/lose_all_on_death/test.py Build/en.gba <scratch>/ss2-en+lose_all_on_death.gba`
with the user's `Savestates/About_To_Die.ss0` (`0f3b2233…`), no input, 750 frames:

| | English | English + mod |
|---|---|---|
| Owner records after death | 16 (hand armour `5/46` and gold removed) | **only `+0x138` soul `7/15`** |
| Ground-item list | `(5,46)` hand armour, `(10,·)` gold | **empty** |
| Wake-up in the inn (area 0) | yes | yes |

Afterwards the character gets up and walks around town normally. A diagnostic check on
`Savestates/Clutch.ss0` (`b0d1bbc4…`): RAM-zeroing the same records, *labelled diagnostic*,
then six attacks, walking, the ring menu and the equipment window. No crash, attacks still
animate, and the window shows ARM/HEAD/BODY/HAND/ACCE and the bag empty with SOUL kept.

**Not tested:** the second hook path `0x0800FB16`; a normal save after death followed by a
reboot. The wipe is a RAM change to the owner record, which the ordinary save copies whole
(`0x0807A9AC`, 0xCAC bytes), so it should persist. As in vanilla, resetting *before* saving
brings back the old save. The user hasn't accepted it yet.

## What the game does on death (English ROM = CN baseline here, `static_verified` + traces)

Found by stepping the emulator one instruction at a time from About_To_Die and watching the
owner record (`find the writer` technique: `s.step(1)` loop + `read8` compare; ~1 s for 1 M steps).

- **Death drop**, in the player death handler (the function around `0x0800F440`, `r7` = player
  actor):
  - gate: `0x0800C8D0()` and `0x0800C710()` both 0, otherwise no drop at all;
  - loop: `r = rand() % 3` (`0x080008C8`, `0x080BAAF4`) picks owner `+0x108` / `+0x118` / `+0x128`;
    an empty slot sets a bit in r6 and retries until all three were tried (mask 7);
  - spawn the picked record with `0x08066A74(actor+0x94 x, actor+0x98 y, record*)`;
  - clear it with `0x08013164(slot 0..2)`, which zeroes the u16 type, the u16 code and the 12
    bytes after them;
  - `0x0805D748`, `…79C`, `…7F0`, `…844`, `…898` refresh per-slot flag bytes for `+0x108` (type 4),
    `+0x118` (3), `+0x128` (5), `+0x138` (7), `+0x148` (6);
  - gold: `0x0805DC70` sums every bag record of type `0x0A` (u32 amount at `+4`), deletes all of
    them and returns **half** (`lsrs #1`). The caller builds `{type 0x0A, amount}` at `sp+0xE0`
    and spawns it. So vanilla drops one armour piece plus half the gold; the other half is gone.
  - A second copy of all this is at `0x0800FB0C..0x0800FBE6` (it compares the type against
    4/3/5 explicitly and calls `0x0805B37C([sp+0x12C]+0x70)` afterwards). `0x080134A6` (character
    reset) also calls `0x08013164`.
- **Owner record layout** (`[0x03003580]`, CN): `+0x78` nine 16-byte weapon records (this
  Warrior used three; character reset `0x080133C0` clears all nine); `+0x108` type 4, `+0x118`
  type 3, `+0x128` type 5 (head/body/hand in some order); `+0x138` soul (type 7); `+0x148` ring
  (type 6); `+0x158` bag 25×16; `+0x2E8` bank 75×16 (first bank record here was gold). The equip
  window labels are ARM, HEAD, BODY, HAND, ACCE, SOUL. `+0x72`/`+0x74` hold small values
  (2, `0x4E20`), not interpreted.

## Ground items (found along the way: the first version *dropped* everything)

The first request was read as "drop everything". That needs more than 16 ground items, so the
system was mapped in full. It's recorded here for anyone touching drops, chests or loot.

- **Spawn event queue:** `0x08066A74(x, y, rec)` and `0x08066B04` (same with an extra u16) don't
  place items directly. They append an event to a queue: base `[0x030063C0]`, count `[0x030063F8]`,
  **max 50** (`cmp #0x31`; returns 0 when full), stride `0x88`. Event: `+0` kind (`0x95` item,
  `0x96` item+u16; others seen: `0x8E`, `0x91`, `0x98`), `+1` 3/4, `+4` 1, `+8` x, `+0xC` y,
  `+0x10` the 16-byte record (copied with `0x080B9A88`, CpuSet). The queue is consumed within a
  few frames; the 16 death drops took ~600 frames to reach the list. Callers include enemy drops
  (`0x080195C6`), bag drops (`0x0807EDC2`) and level scripts.
- **Ground-item list:** a heap block of **16 entries × 0x20** at `[0x03005E18]`, allocated and
  zeroed in task init `0x0805B864` (`alloc(0x200)`) and freed at `0x0805B818`. It's **global**,
  not per map: each entry carries its map id. Entry layout: `+0` x, `+4` y (u32, 1/256 px units),
  `+8` u16 map id (bit `0x20` = keep flag), `+0xA` u16 flags (bit 0 active, bit 1 seen), `+0xC`
  u16 sequence id, `+0xE` = 5, `+0x10` the 16-byte item record. The sequence counter is the u16
  at `0x03005E1C` (wraps after `0xFFFE` to 1). It also serves as an id (`0x0805DB30` looks up by seq).
- **Add:** `0x0805B90C(x, y, map, rec*)`. It counts active entries; **when all 16 are full it
  evicts the oldest** (lowest seq). Then it searches a 21×21 grid for a free tile
  (`0x0800A950` collision, no other entry within 7 px) and fills the first inactive slot.
  `0x0805BB14(&x, &y)` is the same free-tile search, used by the spawner.
- **Every loop over the list** (all `cmp rX,#0xf`): `0x0805B808` (per-frame draw task, calls
  `0x08060364`), `0x0805B896` (init), `0x0805B962`/`B966` (add: scan/count), `0x0805B9FE`,
  `0x0805BAFC`, `0x0805BB9C`, `0x0805BC8E`/`BC92`/`BCC4` (second add path `0x0805BC60`),
  `0x0805D2F6`, `0x0805D522` (per-region counters), `0x0805DA98` (find by position+map),
  `0x0805DB24` (first free), `0x0805DB5C` (by seq), `0x0805DB8C` (flags==2 by seq),
  `0x0805DBB4` (delete by seq), `0x0805DBDA` (clear all), `0x0805DC08` (clear unkept),
  `0x080A1444`.
- **Persistence: the map-state block P** (`[0x030042D0]`, heap, **0x51C bytes**, allocated with
  the owner (0xCAC) in `0x08013214`). P is a snapshot of `world+0x70` (`[0x03005DB4]`):
  `memcpy(P, world+0x70, 0x51C)` at `0x0806267E`/`0x08062A62`, restored by
  `memcpy(world+0x70, P, 0x51C)` at `0x0802270A`. `P+0` is a state word (2/3). **The ground-item
  list is persisted at `P+0x1DC..+0x3DB`** (16 × 0x20):
  - store → list on map load (a switch on the map state): loops at `0x080227AA` (also clears
    `+0xA` unless `+8 & 0x20`), `0x080227F0`, `0x08022968`, `0x08022A78` (these recompute the
    seq counter as max+1);
  - list → store: `0x080626B6` (then save `0x0807A9AC`), `0x080627A4`, `0x080628DA`;
  - store reset (flags `P+0x1E6` = entry `+0xA`, and `P+0x1E8` = `+0xC`): `0x080226E6`,
    `0x08062BCC`, `0x0806565C`, `0x0807ADBE` (new dungeon / give up / load paths);
  - the baseline's own pre-save hook at `0x09000000` (entered from `0x0807A9D0`) CpuSets the
    list into `P+0x1DC` (0x100 halfwords) right before saving.
- **Save layout:** save `0x0807A9AC` allocates two 4 KiB buffers. It copies the owner
  (0xCAC) into one and P (0x51C) into the other, appends a checksum byte `~sum(bytes)` after
  each (`+0xCAC`, `+0x51C`), and writes them to flash sector `slot` and `slot+8`
  (`0x08001B14`; verify `0x08001B54`). Load `0x0807AA94` reads both sectors (`0x08001B04`), checks
  both checksums, then copies them into the owner and P. **The aux sector's bytes
  `0x51D..0xFFF` are unused** (heap garbage at save time). A future mod could store extra
  persistent data there, guarded by its own magic and checksum. `0x0807AB98` writes a zeroed
  aux block (slot erase).
- **Growing the list to 64 (designed, built, then dropped when the request changed):** grow the
  alloc at `0x0805B86C` (`lsls #2` → `#4`), bump the 20 bounds above to 63, allocate P at 0xB30
  (hook `bl alloc` at `0x0801323A`), keep entries 0–15 at `P+0x1DC` and put 16–63 at `P+0x530`.
  The 11 store loops get replaced by helpers. The save (`bl memcpy` at `0x0807A9D8`) appends the
  extension at aux `+0x520` (magic, entries, word checksum) and the load (`0x0807AB2E`) reads it
  back. A first run on About_To_Die put all 16 items in the list. That source was replaced
  before any commit; the description above is enough to rebuild it. Unhandled: link play
  (`0x080627A4`/`0x080628DA` may be link paths) and any code reading `P+0x1DC` that the scan missed.

## Testing note: user savestates vs. changed allocations

A savestate keeps the heap exactly as the old ROM allocated it. A mod that changes an
allocation size can't be tested by loading such a state without fixing RAM first. One method
that worked: run to a Thumb instruction in task context (`run_until(0x0805B80C)`), then save
the registers. Next set `r0 = size`, `lr = <unused ROM address>|1`, `pc = 0x08001494` (heap
alloc) and `run_until` that address. Restore the registers, copy the old block into the new
one and repoint the global. These are diagnostic RAM writes. `lose_all_on_death` changes no
allocations, so its tests don't need this.
